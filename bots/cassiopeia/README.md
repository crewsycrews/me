# Кассеопея

Бот `@casiq_cassiopeia_bot` принимает заявки для Данила Родина. Node.js 24,
стандартные `fetch`, HTTP и `node:sqlite`, без npm-зависимостей и внешней БД.
Telegram работает через **long polling**: бот сам обращается к Bot API по HTTPS.
Публичный домен, webhook и входящий порт для диалога не нужны.

Сценарий:

1. `/start` → приветствие и кнопка «Поделиться контактом».
2. Собственный контакт Telegram → «Как к вам обращаться?».
3. Имя → «Сформулируйте ваш запрос своими словами.».
4. Текст задачи → сохранённая заявка, подтверждение клиенту и уведомление владельцу.

В личку владельца приходят номер заявки, имя, телефон, Telegram username/ID,
полный запрос и атрибуция. Отправка идёт только в `OWNER_CHAT_ID` из конфигурации.
Пользователи не могут выбрать получателя. Если есть username, добавляется кнопка
открытия профиля. Без username доступны телефон и Telegram ID.

`/start` продолжает незавершённую анкету; `/cancel` удаляет её и позволяет начать
заново. После завершения `/start` создаёт новую. `/help` описывает команды.
Контакт другого человека, голосовое сообщение вместо текста и пустой текст
не продвигают анкету. Имя — до 120 символов, запрос — до 4000 символов.

## Настройка и запуск на crews-main-msk

Репозиторий на сервере расположен в `/opt/me`. Нужны Docker и Compose v2
с поддержкой `up --wait`. Из каталога сервиса:

```bash
cd /opt/me/bots/cassiopeia
cp .env.example .env
chmod 600 .env
```

В `.env` заполните `BOT_TOKEN` из BotFather. Username уже указан.
Токен не нужно передавать в чат, коммитить или использовать для публикации в канал.
Используйте отдельного бота, только один запущенный экземпляр сервиса на его токен.

Если ваш числовой Telegram ID неизвестен, пока оставьте `OWNER_CHAT_ID` пустым.
Это режим настройки: заявки не принимаются, `/go` возвращает 503, работает `/whoami`.

```bash
docker compose up -d --build
docker compose logs --tail=50 cassiopeia
```

Откройте [Кассеопею](https://t.me/casiq_cassiopeia_bot), нажмите Start и отправьте
`/whoami` **из своего аккаунта**. Впишите ответ в `OWNER_CHAT_ID`, затем:

```bash
docker compose up -d --force-recreate
docker compose ps
curl -fsS http://127.0.0.1:3088/healthz
```

Ожидается `healthy` и `ok`. В логах `started` с `mode: leads`.
Владелец должен первым начать диалог с ботом: иначе Telegram не разрешит прислать
ему заявку. Параметры не изменяют BotFather автоматически. Имя «Кассеопея» и
[аватарку](assets/cassiopeia-avatar.png) установите через BotFather (`/setname`, `/setuserpic`).
Для меню можно задать `/setcommands`:

```text
start - Оставить или продолжить заявку
cancel - Отменить заполнение
help - Помощь
whoami - Мой Telegram ID
```

Если у этого токена уже есть webhook, сервис завершится с объяснением. Удалите
его осознанно через Bot API либо используйте отдельного бота; сервис сам не
сбрасывает webhook и не удаляет накопленные обновления.

## Автодеплой при push в master

В `.github/workflows/main.yml` задача `deploy-cassiopeia` при каждом push в `master`
выполняется на self-hosted runner с метками `self-hosted`, `linux`, `x64`,
`crews-main-msk`. Runner установлен в `/opt/actions-runner` и работает под
пользователем `github-runner`. Checkout и тесты выполняются в рабочем каталоге
runner; [deploy/deploy.sh](deploy/deploy.sh) обновляет отдельный checkout `/opt/me`.
Задача не зависит от публикации сайта и постов в Telegram, которые по-прежнему
выполняются на GitHub-hosted runner. Push в `main` и `workflow_dispatch` сохраняют
прежний сценарий сайта; бота можно повторно развернуть через Re-run jobs у push-запуска.

SSH secrets для деплоя не нужны. Для `git fetch` используется временный
`GITHUB_TOKEN` задачи с `contents: read`: SSH-адрес origin преобразуется в HTTPS
только на время этой команды, авторизация передаётся через окружение Git.
Токен не сохраняется в `.git/config`, а ключи root не копируются пользователю runner.
`.env` с токеном бота и владельцем остаётся только в `/opt/me/bots/cassiopeia/.env`.

### Runner как systemd-служба

Runner должен быть зарегистрирован для `https://github.com/crewsycrews/me`
с именем и дополнительной меткой `crews-main-msk`, от пользователя `github-runner`.
Токен регистрации вводится один раз в `config.sh`; unit его не содержит.
Для новой регистрации после распаковки официального Linux x64 runner:

```bash
sudo -iu github-runner
cd /opt/actions-runner
read -r -s -p 'Runner registration token: ' RUNNER_REGISTRATION_TOKEN
./config.sh --unattended --url https://github.com/crewsycrews/me \
  --token "$RUNNER_REGISTRATION_TOKEN" --name crews-main-msk \
  --labels crews-main-msk --work _work
unset RUNNER_REGISTRATION_TOKEN
exit
```

Установка службы выполняется штатным `svc.sh` с нашим
[шаблоном systemd](deploy/runner.service.template). Он использует `runsvc.sh`,
включает автозапуск при загрузке и перезапуск после завершения процесса.
После регистрации, если служба ещё не установлена:

```bash
sudo bash /opt/me/bots/cassiopeia/deploy/install-runner-service.sh
```

Служба для указанного имени runner:

```bash
systemctl status actions.runner.crewsycrews-me.crews-main-msk.service
journalctl -u actions.runner.crewsycrews-me.crews-main-msk.service -n 50 --no-pager
```

Ожидается `active (running)`, в логах — `Listening for Jobs`, в GitHub → Settings →
Actions → Runners — `Idle`. Пользователю `github-runner` нужны права записи в
`/opt/me` и доступ к Docker. Добавление в группу `docker` даёт фактически
root-доступ к хосту; runner предназначен для доверенных push в `master`.

Порядок деплоя: блокировка от параллельного запуска → проверка ветки/локальных
правок → `git fetch origin master` → fast-forward до последнего полученного
коммита → проверка Compose → сборка образа → пересоздание `cassiopeia` → ожидание
`healthy` до 180 секунд. Поскольку подтягивается актуальный `master`, он может
быть новее SHA запустившего workflow push; фактический SHA выводится в лог.
`flock` должен быть установлен на сервере (пакет `util-linux`).

Локальные изменения отслеживаемых файлов и отдельные серверные коммиты останавливают
деплой; `reset --hard` не используется. `.env` и Docker volume с SQLite сохраняются.
Ошибка сборки оставляет прежний контейнер работающим. Ошибка запуска/healthcheck
завершает задачу с ошибкой и выводит состояние/последние логи; автоматического
отката контейнера нет. Доступность домена и Caddy проверяется отдельно.

Для ручного запуска того же сценария на сервере нужен доступ к origin по SSH
у запускающего пользователя либо временный `DEPLOY_GITHUB_TOKEN`:

```bash
bash /opt/me/bots/cassiopeia/deploy/deploy.sh
```

## Ссылки с сайта: два режима

**Без публичного HTTP-сервиса:**

```text
https://t.me/casiq_cassiopeia_bot?start=website
```

Это ручной запасной вариант без сервиса атрибуции. В заявке будет `source: website`, без UTM.
Обычный `/start` без ссылки создаёт `source: telegram_direct`.

**С полной атрибуцией (по умолчанию на сайте):** `https://cassey.danilrodin.ru/go`.
Кнопка Telegram на главной и обе кнопки `/consulting` (также на английских страницах)
используют этот адрес. Опубликуйте HTTP `/go` через HTTPS reverse proxy на
`127.0.0.1:3088`. Этот endpoint нужен для записи UTM и редиректа, а не для webhook.
Сайт статический и размещён на GitHub Pages, поэтому сам записывать UTM в БД не может.

В DNS зоны `danilrodin.ru` создайте A-запись `cassey` с публичным IPv4 сервера
`crews-main-msk`. AAAA добавляйте только при настроенном IPv6 на этом сервере.
Для HTTPS на сервере должны быть доступны входящие 80/443 и настроен Caddy.
Готовый блок находится в [deploy/Caddyfile](deploy/Caddyfile): подключите его
к существующей конфигурации Caddy на хосте, сохранив остальные сайты.

```caddyfile
cassey.danilrodin.ru {
    @lead path /go
    handle @lead {
        reverse_proxy 127.0.0.1:3088
    }
    handle {
        respond "Not found" 404
    }
}
```

У контейнерного proxy `127.0.0.1` указывает на сам контейнер: в этом случае
подключите сервисы к общей Docker network и используйте `cassiopeia:3000`.
Локальный `/healthz` не требуется публиковать. Не записывайте query string `/go`
в access logs proxy: там находятся UTM. Входящий порт 3088 в Compose привязан к loopback.
Для бота нужен исходящий доступ к `api.telegram.org:443`.

Адрес уже задан в `nuxt.config.ts`; дополнительная GitHub variable не обязательна.
При необходимости переопределить его используйте GitHub → Settings → Secrets
and variables → Actions → **Variables**:

```text
NUXT_PUBLIC_LEAD_BOT_URL=https://cassey.danilrodin.ru/go
```

После этого пересоберите и опубликуйте сайт обычным процессом. Локальная генерация:

```bash
npm run generate
```

Это публичная настройка, токены в неё не входят. Без JavaScript ссылка `/go`
всё равно помечает источник как сайт, но атрибуция исходной страницы недоступна.

Как сохраняется атрибуция:

- `public/lead-attribution.js` запоминает первый вход и последнее посещение с UTM
  в `sessionStorage` текущей вкладки, максимум на 30 дней. Переходы без UTM не
  затирают последнюю кампанию. Между устройствами и независимыми вкладками данные
  не объединяются. Если storage заблокирован, доступны данные текущего документа/SPA.
- Сохраняются все параметры `utm_*`, включая нестандартные, повторяющиеся,
  кириллицу и пустые значения. Остальная query string не собирается.
  Сохраняются пути страниц, время и реферер без query/fragment.
- Клик ведёт на `/go?attribution=...`. Сервис сначала пишет данные в SQLite,
  затем отвечает 302 на `t.me/...?...start=web_<случайный идентификатор>`.
  ID имеет 28 символов. [Telegram допускает только 64 символа в start](https://core.telegram.org/bots/features#deep-linking),
  поэтому полный набор UTM не передаётся напрямую в Telegram.
- После `/start` данные копируются из перехода в анкету, а затем в заявку.
  Новый атрибутированный `/start` обновляет атрибуцию текущей анкеты, сохраняя ответы;
  простой `/start` её не стирает. Токен живёт 30 дней и допускает повторное открытие.
  Истёкший/неизвестный `web_...` отмечается явно, без выдуманных UTM.
- Атрибуция — заявленные браузером маркетинговые данные: ссылку можно переслать
  или подделать. Она не доказывает подлинность источника и не используется для доступа.
- Ограничения: до 100 UTM-пар на касание, значение до 4096 символов, весь JSON до
  16 КиБ, закодированная ссылка до 48 КиБ; превышение возвращает ошибку без обрезки.
  Proxy/браузер может иметь меньший предел URL. `/go` допускает 120 запросов/минуту
  на процесс; при превышении возвращает 429. `start=website` служит ручным запасным
  вариантом, если сервис атрибуции недоступен.

Можно использовать и ручную ссылку кампании:

```text
https://cassey.danilrodin.ru/go?utm_source=yandex&utm_medium=cpc&utm_campaign=consulting
```

## Надёжность, данные и эксплуатация

В SQLite одной транзакцией сохраняются шаг анкеты, заявка, исходящие сообщения
и offset Telegram. Повторно полученный update не создаёт вторую заявку.
Docker volume `cassiopeia-data` сохраняет БД при пересоздании контейнера.

Очередь повторяет неудачные отправки с задержкой, учитывает `retry_after` и
сохраняет порядок для каждого получателя. Ошибка отправки одному пользователю
не блокирует других. При сетевом таймауте Telegram мог принять сообщение до
разрыва соединения: повтор уведомления возможен; номер заявки остаётся прежним.
Заявка в БД одна. Подтверждение клиенту означает сохранение заявки, а не
подтверждённую доставку владельцу.

`/healthz` отвечает 503, если polling не отвечал более 2 минут или есть исходящее
сообщение старше 10 минут. Docker помечает контейнер unhealthy; сам по этому
статусу его не перезапускает. Смотрите `delivery_retry` / `poll_retry` и код:
403 обычно означает блокировку бота, 400 — недоступный chat, 429 — ограничение
частоты. После исправления доставка повторяется, максимум раз в час.
Логи не содержат телефона, текста заявки, UTM или токена.

Незавершённые анкеты и переходы удаляются через 30 дней, успешно отправленные
записи очереди — через 7 дней. Готовые заявки и неотправленные сообщения хранятся
до ручного удаления. БД содержит контакты: доступ к серверу и резервным копиям
должен быть только у владельца. Удаление анкеты не удаляет уже отправленную заявку.

Резервная копия без гонки с SQLite WAL (краткая остановка сервиса):

```bash
docker compose stop cassiopeia
docker compose cp cassiopeia:/app/data ./backup-cassiopeia
docker compose start cassiopeia
```

Выберите новый каталог для каждой копии. Копируйте весь каталог, включая WAL/SHM,
если они присутствуют. Не выполняйте `docker compose down -v`: это удалит volume.

## Проверки

Из корня репозитория под Node.js 24:

```bash
npm run test:leads
```

Либо из каталога бота: `npm test`. Проверки используют временную SQLite,
локальный HTTP и подставной Telegram API; реальные сообщения не отправляются.
Проверяются сценарий, свой/чужой контакт, повтор update, откат транзакции,
перезапуск с незавершённой анкетой, очередь/retry, длинные сообщения и UTM.

После развёртывания проверьте вручную:

1. Откройте сайт с `?utm_source=test&utm_campaign=кассеопея&utm_custom=a%26b`.
2. Перейдите на `/consulting`, затем в бота, нажмите Start, пройдите три шага.
3. В личке владельца должны появиться контакт, имя, полный запрос, исходная
   страница и все три UTM. Без HTTP-режима будет только источник «сайт».
4. Перезапустите контейнер посередине другой анкеты и продолжите — шаг сохранится.
5. Отправьте `/start` напрямую после завершённой заявки — источник новой будет `telegram_direct`.

Docker-образ и полная генерация сайта не проверены в рамках реализации; их
сборка и реальная проверка Telegram выполняются при развёртывании.
